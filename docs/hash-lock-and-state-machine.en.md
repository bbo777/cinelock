# How I Used Hash Locks and a State Machine to Fix Multi-Model AI Video Continuity

> Five shots, four providers, twenty variants — all compiled from the same context revision `3363f8fde6e7`.
> The project also ships a zero-dependency MCP server so agents can query the lock directly.

When you generate the same scene with multiple AI video models, the failure mode is predictable:

- Shot 1 has the character in a dark trench coat with a cut above the left eyebrow.
- Shot 2, generated by another provider, gives him a black jacket and no injury.
- Shot 3 switches back to fix it, but the lighting has moved from dusk to noon.
- By shot 4, nobody remembers which reference image was final, which prompt was used, or which version of the character card was loaded.

The result is not one film. It is four films that happen to share a script.

The core contradiction is simple: **probabilistic models are non-deterministic; narrative continuity is not negotiable.** Prompt engineering alone cannot close that gap, because the model never sees "the previous shot" — it only sees whatever context you hand it this time.

NineFlow is a local orchestration layer built around a different premise: don't try to make the model deterministic. Make the **input, the state, and the evidence** deterministic.

## 1. Define consistency as four checkable dimensions

"Character consistency" is too vague to test. I break it into:

1. **Identity** — face, hair, build, wardrobe baseline.
2. **State** — injuries, props, and wardrobe changes must happen in story order.
3. **Scene** — location, time of day, lighting, and composition come from one timeline.
4. **Provenance** — every output can be traced to a provider, a context revision, a prompt, and a set of reference hashes.

Most pipelines only handle the first dimension: feed the model the same face and hope. NineFlow turns all four into data structures, then locks them.

## 2. The hash lock: make context a verifiable object

`context_revision` is a SHA-256 over the project config, character cards, reference bank, timeline, provider matrix, prompt maps, actual asset hashes, and an engine fingerprint.

The subtle part is the reference bank. If you hash the JSON file as-is, you get two bad outcomes:

- Replace an image but leave the recorded hash untouched: the revision does not change.
- Correct the recorded hash: the revision changes even though no image changed.

So the revision is computed after replacing every recorded `sha256` with the **actual file hash**:

```python
def normalized_bank(self):
    bank = copy.deepcopy(self.bank_doc)
    for asset in bank.get("assets") or []:
        asset["sha256"] = self.asset_hash(asset) or ""
    return bank
```

Now the semantics are right:

- image bytes change → actual hash changes → revision changes;
- bookkeeping is corrected → normalized content is unchanged → revision does not change.

**Lock the fact, not the ledger.**

The engine fingerprint covers the NineFlow version plus the source hashes of the context, compiler, and continuity modules. If the compiler changes, old jobs become "historical context" instead of being silently treated as current.

Every job records the full `source_hashes`, the engine fingerprint, the per-shot snapshot hash, prompt hashes, variant hash, reference hashes, provider, seed, outputs, and media probe results. Execution refuses to start if the current revision no longer matches the pack. Audit recomputes everything afterward.

### Repairing hashes must be safe

After the lock landed, a real operational problem appeared: replace a reference image and validation correctly reports a hash mismatch. The old advice was "edit the JSON by hand", which is both error-prone and hides the fact that the file changed.

`refresh-hashes` does something different:

1. Recompute the SHA-256 of every asset.
2. If any file is missing or unreadable, refuse the whole operation and write nothing.
3. Otherwise, atomically rewrite the bank and refresh the in-memory document.
4. Refreshing itself does not change the revision — the image bytes already did.

A constraint without a safe repair path is a constraint people will bypass.

### Partial builds must not poison shared state

Another production bug: `build --provider mock` wrote the shared Context Pack, so compiling one provider removed every other provider's variants from it. The next provider saw a "current" pack that did not contain it.

The fix was semantic, not a patch: `--provider` is now preview-only (`written: false`, `pack_path: null`). Only a full build may write the shared pack, and it clears the per-shot output directory first so disabled providers cannot leave stale variants behind.

## 3. The state machine: continuity is a transition, not an adjective

Character cards define the initial state. Every subsequent change must appear in the timeline as a `state_delta`:

```json
{
  "state_delta": {
    "CH_LINYE_01": {
      "add_injuries": ["left brow laceration"],
      "add_props": ["blood-stained baseball"],
      "wardrobe_state": "dark trench coat, rain-soaked"
    }
  }
}
```

Application order is fixed: remove, then add; sets are de-duplicated; unspecified fields carry forward. The timeline is walked once to produce a canonical snapshot for every shot. The compiler consumes the snapshot, not the raw character card.

This distinction matters. A character card says who someone is. A snapshot says who they are **in this shot**. All four providers receive the same snapshot, so none of them gets to infer a different costume or injury state.

Using incremental deltas instead of a single final state preserves *when* a change happened. Audit can replay the timeline and compare every field against the snapshot recorded with the job. If one field differs, it reports the exact difference.

## 4. Deterministic compilation

The compiler fixes block order, reference priority, truncation rules, duration rounding, seed handling, and negative-prompt merging. Recompiling the same shot for the same provider under the same revision must produce the same prompt hash.

The audit includes a `recompile` check for exactly this reason. Without it, "reproducible" is just a claim.

In the demo project: 5 shots × 4 providers = 20 variants, 56 reference usages, one revision.

## 5. Layered audit: evidence is not the same as job outcome

The first audit implementation had a single pass/warn/fail status, which conflated two questions:

- Is the **evidence chain** intact? Do hashes, snapshots, prompts, and references match?
- Did the **job** succeed? Was it a dry run, a provider failure, a block, or a real success?

A failed provider call could look like an evidence failure; a job with intact evidence but stale context could look like a pass.

The report now separates:

- `artifact_status` / `scope: artifact_integrity` — the evidence chain;
- `job_status` / `dry_run` — what actually happened;
- `verdict.overall` — the composite conclusion.

Thirteen checks cover provenance, revision lock, engine fingerprint, snapshot integrity, state-machine replay, prompt integrity, reference hashes, output hashes, recompilation, continuity coverage, reference projection, current revision, and pack consistency.

A recent mock job passed all 13, with `job_status: succeeded`, `current_context: current`, and `overall: pass`. A real handoff job also audited with exit code 0.

## 6. ffprobe and contact sheets: making outputs checkable

Hashes prove a file was not swapped; they do not prove it plays. Downloads are now probed with ffprobe for duration, resolution, codec, and container. A failed probe fails the job; a missing ffprobe downgrades to a warning instead of pretending validation happened.

ffprobe validates the container and streams, not the picture. For visual review, ffmpeg builds a 3×3 contact sheet at 1920×1080 with nine evenly spaced frames. It is available from the CLI and from the local dashboard.

On a real handoff output, the sheet was 1920×1080 and about 278 KB, with frame timestamps from 0.28s to 4.72s; the source probed as 5.0s, 1920×1080, H.264.

Neither tool replaces a human review. They just move obvious failures earlier.

## 7. MCP / API access: let an agent call the lock

NineFlow ships a zero-dependency MCP stdio server. It runs on Python 3.8 without the official SDK, and calls the same engine as the CLI: same revision, same state machine, same audit checks.

Add this to Claude Desktop's `claude_desktop_config.json` (Windows: `%APPDATA%\Claude\claude_desktop_config.json`), then restart the client:

```json
{
  "mcpServers": {
    "nineflow": {
      "command": "python",
      "args": ["C:/path/to/nineflow/studio.py", "--project-dir",
               "C:/path/to/nineflow/projects/nine-inning-bottom", "mcp"],
      "env": {"PYTHONIOENCODING": "utf-8"}
    }
  }
}
```

WorkBuddy uses the same shape in `%USERPROFILE%\.workbuddy\mcp.json`. Replace the path with your checkout; use `/` in Windows paths, or escape backslashes as `\\`. If the client cannot find `python`, point `command` at the absolute interpreter path.

The server exposes seven tools:

- `nineflow_status` — revision, shots, providers, pack state, validation summary;
- `nineflow_validate` — character cards, reference hashes, timeline, provider config;
- `nineflow_variant` — compiled prompt, references, and continuity snapshot for one shot × provider (in-memory only);
- `nineflow_audit` — the 13-check evidence audit for a job;
- `nineflow_jobs` — recent jobs, filterable by shot or provider;
- `nineflow_build` — preview by default; `write=true` performs a full build;
- `nineflow_contact_sheet` — 3×3 contact sheet from a job's local video.

The boundaries are deliberate: stdio only, no listening port, no network calls; the project directory is fixed at process launch; `write=true` must be explicit and cannot be combined with a single-provider preview; Quota-Flow credentials are never exposed through MCP.

MCP is not a label here. It is the natural distribution surface for the constraints: an agent can query the revision, fetch a compiled variant, and run the audit without reimplementing any of the semantics — and without summarizing away the layered verdict.

## 8. What this does not solve

- It does not eliminate model randomness.
- It does not guarantee visual quality or acting.
- It does not replace a director.
- It does not auto-fix continuity errors; it detects, blocks, and records them.
- It is only as good as the timeline's `state_delta`. Bad continuity data is propagated faithfully — garbage in, garbage out, but now with a hash.

NineFlow is not a video model. It is a continuity and evidence layer above models.

## 9. The lesson

Hash locks make sure every provider sees the same facts. The state machine makes sure they see the same facts *at the same point in time*. Deterministic compilation makes sure they receive the same instructions. Layered audit makes sure that when something breaks, you can prove which layer broke first.

Consistency is not about making models non-random. It is about keeping randomness inside a controlled boundary — and being able to explain every crossing.
