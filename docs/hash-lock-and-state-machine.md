# 我是如何用哈希锁和状态机，解决 AI 视频跨模型一致性灾难的

> 5 个镜头、4 个模型、20 个变体，共享同一份上下文修订 `3363f8fde6e7`。
> 这不是一篇“提示词玄学”，而是一次把一致性变成可验证约束的工程尝试。
>
> 关键词：MCP Server · 哈希锁 · 连续性状态机 · 多模型 AI 视频

## 一、灾难现场：每个模型都在“自由发挥”

如果你用多个 AI 视频模型做过同一场戏，大概率见过下面这些画面：

- 第 1 个镜头里，男主穿深灰风衣、左眉有伤；
- 第 2 个镜头换了一个模型，风衣变成黑色夹克，伤口消失了；
- 第 3 个镜头为了“修复”，又换回第一个模型，结果场景从黄昏变成了正午；
- 到第 4 个镜头，你已经记不清哪张参考图是“最终版”，也说不清上一版提示词到底改了什么；
- 最后你把四段视频拼在一起，观众第一眼就看出来：这不是同一个人。

更麻烦的是，你无法复盘。

你只知道“图不对”，但不知道是角色卡被覆盖了、参考图换了、模型没吃到图、提示词编译顺序变了，还是任务跑的根本不是你以为的那一版上下文。于是只能重新抽卡：再生成、再对比、再猜测。时间、算力和配额，全部消耗在“找回上一次的正确状态”上。

这就是 AI 视频工业化道路上最核心的矛盾：

> **概率模型天然不确定，而影视叙事要求绝对连续。**

只要你在多个模型之间切换，这个矛盾就会被放大。因为每个模型都有自己的提示词偏好、参考图上限、时长取整、首帧策略和失败方式。你越依赖“把同一段提示词复制过去”，越容易得到四部不同的电影。

我的结论是：**不要试图让模型变得确定，要让模型的输入、状态和证据变得确定。**

NineFlow 就是围绕这句话做的一套本地编排层。它不生成视频，而是确保每个模型在开工前拿到同一套参考图、同一套角色卡、同一条时间线，并且在生成后能证明“它确实用的是这一版”。

## 二、先定义“一致”到底是什么

“角色一致”是一个太模糊的词。模糊的目标无法测试，也无法审计。我把它拆成四个可以被机器检查的维度：

1. **身份一致**：同一个角色，脸、发型、体型、服装基准不能漂。
2. **状态一致**：伤口、道具、服装变化必须按剧情顺序发生，不能第 3 镜受伤、第 2 镜就有疤。
3. **场景一致**：地点、时间、光线、构图要来自同一条时间线。
4. **执行一致**：某个产物到底由哪个模型、哪一版上下文、哪一份提示词生成，必须可追溯。

前三个维度决定“看起来连不连”，第四个维度决定“出问题能不能查”。

大多数工作流只做第一维：给模型喂同一张脸。然后祈祷剩下三维不出错。NineFlow 的做法是四维都变成数据结构，再分别加锁。

## 三、哈希锁：把“上下文”变成一个可验证对象

### 3.1 一次修订，锁住所有输入

NineFlow 的项目目录里有几份人类可读的源文件：项目配置、角色卡、参考图清单、时间线、模型矩阵、提示词映射。它们共同决定一次生成的全部输入。

`context_revision` 不是时间戳，也不是自增编号，而是这些输入的 SHA-256：

```python
def source_hashes(self) -> Dict[str, Any]:
    assets = {}
    for asset in self.asset_list():
        aid = asset.get("asset_id")
        if not aid:
            continue
        assets[aid] = self.asset_hash(asset) or "missing"
    return {
        "project": sha256_json(self.project),
        "characters": sha256_json(self.characters_doc),
        "reference_bank": sha256_json(self.normalized_bank()),
        "timeline": sha256_json(self.timeline),
        "providers": sha256_json(self.provider_profiles()),
        "prompt_maps": sha256_json(self.prompt_maps),
        "assets": assets,
        "engine": self.engine_fingerprint(),
    }

def context_revision(self) -> str:
    return sha256_json(self.source_hashes())
```

这里有一个很容易被忽略、但非常关键的细节：**参考图清单里的 `sha256` 字段，不能直接拿来算修订。**

如果直接对 `reference_bank.json` 的原始内容做哈希，会得到两个荒谬的结果：

- 你换了图片文件，但只要 JSON 里记录的旧哈希没改，修订不变；
- 你只是把 JSON 里记录的哈希修正为真实值，修订却变了。

前者让哈希锁形同虚设，后者让“修复哈希”变成一次毫无意义的上下文变更。

所以 `normalized_bank()` 在计算修订前，会把每个资产记录的 `sha256` 替换成**文件当前的真实哈希**：

```python
def normalized_bank(self) -> Dict[str, Any]:
    bank = copy.deepcopy(self.bank_doc)
    for asset in bank.get("assets") or []:
        asset["sha256"] = self.asset_hash(asset) or ""
    return bank
```

这样一来，语义就正过来了：

- **图片字节变了** → 真实哈希变 → 修订变；
- **只修正账本里记错的哈希** → 归一化后不变 → 修订不变。

这就是哈希锁的第一条原则：**锁的是事实，不是账本。**

### 3.2 引擎也要进锁

只锁项目文件还不够。如果编译器改了提示词拼接顺序，或者状态机改了字段合并规则，同一份项目输入也可能产出不同的提示词。

所以 `source_hashes` 里还有一项 `engine`：NineFlow 版本号，加上 `context.py`、`compiler.py`、`continuity.py` 三个核心文件的哈希。编译器一变，修订就变；旧任务会被标记为“历史上下文”，而不是被假装成“当前”。

这不是为了追求形式上的严格，而是为了避免一种更隐蔽的灾难：**代码升级后，旧任务的审计结果突然全部失真，但没人知道为什么。**

### 3.3 任务账本记录的不只是 revision

每次执行，任务账本会写下：

- `context_revision` 与完整的 `source_hashes`；
- 引擎指纹；
- 该镜头的上下文快照及其哈希；
- 编译后的正向/负向提示词哈希；
- 变体哈希；
- 参考图列表与每张图的 SHA-256；
- 模型、适配器、模式、时长、种子；
- 产物路径、媒体探测结果；
- 失败原因与警告。

生成前，系统会检查当前上下文修订是否与任务记录一致；不一致就拒绝执行。生成后，审计会重新计算这些哈希，逐项对照。

于是“这一版到底用了哪张图、哪句提示词、哪版代码”不再依赖人的记忆，而是变成可重放的证据。

### 3.4 修复哈希：是修复，不是绕过

哈希锁上线后，立刻遇到一个真实的运维问题：用户换了一张参考图，校验报“哈希不一致”。旧做法是让用户手动去改 `reference_bank.json` 里的 `sha256`。这既容易改错，也容易把“文件已经换了”这件事掩盖过去。

新增的 `refresh-hashes` 做的是另一件事：

1. 逐个读取资产文件，重新计算真实 SHA-256；
2. 只要有一个文件缺失或不可读，**整体拒绝，不写回任何内容**；
3. 全部可读时，原子写回参考图清单，并刷新内存中的文档；
4. 刷新本身不改变 `context_revision`——真正改变修订的，是图片字节，而不是这次修复动作。

这看起来只是一个小命令，但它决定了哈希锁是“可用的工程约束”，还是“每次都要手改 JSON 的麻烦”。约束必须配有安全的修复通道，否则人一定会绕过它。

### 3.5 共享上下文不能被“部分构建”污染

这是另一个很典型的 P0：`build --provider mock` 原本会写共享的 Context Pack。结果只编译了一个模型，却把其他模型的变体从共享包里抹掉了。下一个模型执行时，看到的是一个“修订号很新、但没有自己”的包。

修复方式不是加更多判断，而是改变语义：

- `--provider` 只做**预览**：返回 `written: false`、`pack_path: null`，不碰共享包；
- 只有全量构建才写入 `context/context_pack.json` 和每个镜头的变体文件；
- 每次全量写入前，先清空 `context/shots`，避免已禁用模型的旧变体残留。

共享可变状态最怕“看起来成功”。所以这里宁可让部分构建“只读”，也不让它拥有写权限。

## 四、状态机：连续性不是形容词，是状态转移

### 4.1 时间线是唯一的状态变更源

角色卡定义初始状态：基准服装、已有伤情、随身道具。之后的所有变化，只能写在时间线的 `state_delta` 里：

```json
{
  "shot_id": "E01-003",
  "character_ids": ["CH_LINYE_01"],
  "continuity": {
    "from_shot": "E01-002",
    "state_delta": {
      "CH_LINYE_01": {
        "add_injuries": ["左眉裂伤"],
        "add_props": ["染血棒球"],
        "wardrobe_state": "深灰风衣·雨湿"
      }
    },
    "notes": "暴雨夜，投手丘"
  }
}
```

应用规则很简单，但必须是确定性的：

```python
def apply_state_delta(state, delta):
    out = {
        "wardrobe_state": state.get("wardrobe_state"),
        "injuries": list(state.get("injuries") or []),
        "props": list(state.get("props") or []),
    }
    if delta.get("wardrobe_state"):
        out["wardrobe_state"] = delta["wardrobe_state"]
    out["injuries"] = _remove(out["injuries"], delta.get("remove_injuries"))
    out["injuries"] = _add_unique(out["injuries"], delta.get("add_injuries"))
    out["props"] = _remove(out["props"], delta.get("remove_props"))
    out["props"] = _add_unique(out["props"], delta.get("add_props"))
    return out
```

注意它的顺序：**先移除，再添加；集合去重；未声明的字段保持不变。** 这些细节决定了重放是否可重复。状态机最怕“差不多”，因为“差不多”在不同模型、不同轮次里会累积成肉眼可见的穿帮。

### 4.2 为每个镜头生成快照

遍历一次时间线，为每个镜头产出规范快照：

```json
{
  "shot_id": "E01-003",
  "from_shot": "E01-002",
  "scene": {"location_en": "rain-soaked baseball mound", "time_of_day": "night"},
  "characters": {
    "CH_LINYE_01": {
      "wardrobe_state": "深灰风衣·雨湿",
      "injuries": ["左眉裂伤"],
      "props": ["染血棒球"],
      "expression": "咬牙"
    }
  },
  "changes": {"CH_LINYE_01": ["injury + 左眉裂伤", "prop + 染血棒球"]}
}
```

关键点：**编译器消费的是快照，不是角色卡原文。**

角色卡描述“这个人是谁”，快照描述“这个人此刻是什么状态”。四个模型拿到的都是同一份快照，所以它们不会各自从角色卡出发，自行推断“这场戏应该穿什么”。

快照还会被渲染成人类可读的连续性约束，进入提示词，而不是只躺在 JSON 里。否则状态机只是自娱自乐，模型根本不知道。

### 4.3 为什么用增量，而不是最终状态

最省事的做法是：先算出每个角色在故事结尾的状态，然后所有镜头都用它。但这会直接毁掉叙事：

- 第 2 镜不该有第 5 镜才出现的伤；
- 第 4 镜脱掉的外套，不能在第 3 镜就消失；
- “从上一镜继承”这件事，必须能被审计，而不是靠最终状态反推。

增量状态机保留了“变化发生在哪一镜”的信息，所以审计可以按时间线重放，逐字段对比任务记录的快照。只要有一个字段对不上，`continuity_replay` 就会给出具体差异，而不是一句笼统的“状态不一致”。

这也是 NineFlow 和“把角色描述拼进提示词”最本质的区别：**前者有状态，后者只有形容词。**

## 五、确定性编译：同一修订，必须得到同一份提示词

有了锁和状态，还需要保证编译过程本身不引入随机性。

NineFlow 的编译器做了几件很朴素的事：

- 按固定顺序拼接：任务 → 风格 → 场景 → 角色身份 → 连续性状态 → 参考图图例 → 运镜/动作 → 负向约束；
- 参考图池按固定优先级排序：身份锚点优先，其次场景、道具、风格；
- 超过模型 `max_refs` 时，按确定规则截断，并给出警告，而不是随机丢图；
- 时长按模型能力取整，并记录取整原因；
- 种子固定，变体哈希由编译结果计算；
- 负向提示词按固定顺序合并、去重。

最终，每个“镜头 × 模型”的组合都会得到一个 `variant_sha256`。同一个修订、同一个镜头、同一个模型，重复编译必须得到同一个哈希。

审计里的 `recompile` 检查就是干这个的：它用当前代码重新编译，和任务记录里的提示词哈希对比。如果对不上，说明编译器存在隐藏的非确定性，或者代码已经变了。这个问题如果不查，所谓“可复现”就是一句空话。

在演示项目里，5 个镜头 × 4 个模型 = 20 个变体，累计引用参考图 56 次，全部共享同一个修订：

```text
context_revision = 3363f8fde6e766840b637a4baf551e6318637894c4fb57906fc58f558212d318
short            = 3363f8fde6e7
variants         = 20
providers        = mock / qwenwan / yuanbao / handoff
```

注意，这不是“20 个视频”，而是 20 份**可执行、可审计的生成说明书**。其中 mock 与 handoff 可以先跑通全链路，真实模型走各自的适配器；没有配额时，也不会阻塞整个流程。

## 六、审计分层：别把“证据链”和“任务结果”混为一谈

### 6.1 原来的问题

最早的审计只有一个 `status`：pass / warn / fail。它把两件不同的事混在了一起：

- 这份产物的**证据链**是否完整？哈希、快照、提示词、参考图能不能对上？
- 这次**任务**本身是否成功？模型有没有报错、超时、被阻断，或者只是演练？

结果就是：一个模型调用失败的任务，可能因为“没有产物”而被判成证据链失败；一个证据链完整但上下文已经过期的任务，又可能显示成 pass。人看到的结论和实际风险不一致。

### 6.2 分层后的语义

现在审计报告同时给出三层信息：

```json
{
  "ok": true,
  "status": "pass",
  "artifact_status": "pass",
  "scope": "artifact_integrity",
  "job_status": "succeeded",
  "dry_run": false,
  "verdict": {
    "artifacts": "pass",
    "job": "succeeded",
    "job_ok": true,
    "current_context": "current",
    "overall": "pass"
  }
}
```

- `status` / `artifact_status`：只回答“证据链是否自洽”；
- `job_status` / `dry_run`：回答“这次任务实际发生了什么”；
- `verdict.overall`：综合结论。证据链失败 → fail；任务失败、上下文过期或历史任务 → 至少 warn；
- CLI 退出码和顶层 `ok` 仍然只反映证据链，避免把“模型失败”误报成“审计失败”。

这个区分非常重要。因为**证据链完整，不代表任务成功；任务成功，也不代表用的是当前上下文。** 两者必须分开看，否则审计会变成一句没有信息量的“通过/不通过”。

### 6.3 13 项检查

一次完整的审计会检查：

1. `provenance`：任务是否带上下文存证；
2. `revision_lock`：存证的 `source_hashes` 是否与任务修订一致；
3. `engine`：编译引擎是否与当前一致；
4. `snapshot_integrity`：上下文快照哈希是否一致；
5. `continuity_replay`：按时间线重放 `state_delta`，逐字段对比；
6. `prompt_integrity`：正向/负向提示词哈希是否一致；
7. `references`：参考图实际文件是否与任务记录一致（离线核验，不访问外链）；
8. `outputs`：产物是否存在、大小与哈希是否一致；
9. `recompile`：同修订重编译是否得到同一提示词；
10. `continuity_coverage`：该镜头涉及的角色是否都有状态快照；
11. `reference_projection`：参考图是否正确投影到该变体；
12. `current_revision`：任务上下文相对当前项目是否过期；
13. `pack`：Context Pack 是否存在且与当前修订一致。

最近一次 mock 任务的结果是 13 项全部 pass，任务状态 succeeded，上下文 current，综合结论 pass。真实 handoff 任务的审计也以退出码 0 通过。

这 13 项里，没有一项依赖“看视频猜”。它们全是可重算的哈希、可重放的状态和可对照的文件。**审计不是主观判断，而是证据核对。**

## 七、ffprobe 与九宫格：把“看起来对”变成可检查的产物

哈希能证明“文件没被换”，但不能证明“文件能播”。所以下载链路接入了 ffprobe：

```text
ffprobe -v error \
  -show_entries format=duration,size,format_name:stream=index,codec_type,codec_name,width,height,duration \
  -of json <video>
```

拿到时长、分辨率、编码、容器格式后，写入任务账本和产物元数据。探测失败的任务直接标记失败；系统里没有 ffprobe 时，降级为警告，而不是假装校验过。

这里必须说清楚边界：**ffprobe 校验的是容器与流，不是画面内容。** 它不能告诉你角色有没有穿帮，只能告诉你这个文件是不是一个可解码的视频。

那“画面内容”怎么办？加一个 ffmpeg 九宫格：

```text
fps = 帧数 / 时长
tile = 3x3
输出 = 1920x1080
```

把视频按时间均匀抽 9 帧，缩放、补边、拼成一张 3×3 联系表。CLI 可以直接对任务或本地视频生成，dashboard 的任务抽屉里也有一键“生成九宫格”。

它的价值不是“自动化审片”，而是把跨模型对比的成本从“逐个播放”降到“扫一眼”：

- 同一镜头，四个模型的九宫格并排看，身份、服装、场景漂移会非常明显；
- 同一模型的不同版本，抽帧时间点固定，变化可比较；
- 真实 handoff 产物上，九宫格输出为 1920×1080，约 278 KB，9 帧时间戳从 0.28s 到 4.72s；
- 对一条 5.0 秒、1920×1080、H.264 的下载视频，ffprobe 也能给出稳定的媒体信息。

九宫格是给人看的，ffprobe 是给机器看的。两者都不能替代最终的人工审片，但能把“明显不对”的产物尽早挡在剪辑之前。

## 八、MCP / API 接入：让 Agent 直接调用哈希锁

如果每次查修订、取提示词、跑审计都要人肉敲 CLI，这套约束就只属于我一个人。MCP 把它变成一个任何 Agent 客户端都能调用的工具面。

NineFlow 内置了一个零依赖的 MCP stdio Server，兼容 Python 3.8，不需要安装官方 SDK，也不需要额外的 API Key。它和 CLI 调用的是同一套引擎：同一个修订、同一份状态机、同一组审计检查。

### 10 行配置

把下面这段加入 Claude Desktop 的 `claude_desktop_config.json`：

```json
{
  "mcpServers": {
    "nineflow": {
      "command": "python",
      "args": ["C:/path/to/nineflow/studio.py", "--project-dir",
               "C:/path/to/nineflow/projects/nine-inning-bottom", "mcp"],
      "env": {"PYTHONIOENCODING": "utf-8"}
    }
  }
}
```

WorkBuddy 使用同一段配置，写入 `%USERPROFILE%\.workbuddy\mcp.json`；如果文件里已有其他 server，把 `nineflow` 这一项合并进 `mcpServers` 即可。

把 `C:/path/to/nineflow` 换成仓库实际路径。若客户端找不到 `python`，把 `"command"` 换成 `where python` 返回的绝对路径。JSON 里的 Windows 路径请使用 `/`，或把 `\` 转义为 `\\`。

### 七个工具

| 工具 | 作用 | 是否写入 |
| --- | --- | --- |
| `nineflow_status` | 当前修订、镜头、厂商、Pack 状态与校验摘要 | 否 |
| `nineflow_validate` | 校验角色卡、参考图哈希、时间线与厂商配置 | 否 |
| `nineflow_variant` | 读取某个镜头 × 厂商的提示词、参考图与连续性快照 | 否（仅在内存编译） |
| `nineflow_audit` | 按 `job_id` 运行 13 项证据链审计 | 否 |
| `nineflow_jobs` | 列出任务账本，可按镜头/厂商过滤 | 否 |
| `nineflow_build` | 编译 Context Pack；默认只预览，`write=true` 才全量写入 | 显式调用时 |
| `nineflow_contact_sheet` | 从任务视频生成 3×3 抽帧九宫格 | 写入 `outputs/` |

配置完成后，可以直接在 Claude Desktop 或 WorkBuddy 里说：

- “用 nineflow_status 看一下当前修订和 5 个镜头。”
- “把 E01-004 × mock 的完整提示词和参考图给我。”
- “审计 JOB_...，分别告诉我证据链结论和任务状态。”

### 为什么不是“给项目贴个 MCP 标签”

MCP 在这里不是一层营销包装，而是这套约束的自然出口：

- **同一个事实源**：MCP 工具不维护第二份配置，读到的就是 CLI 和看板看到的那份 Context Pack；
- **同一个写边界**：`nineflow_build` 默认只预览，写共享包必须显式 `write=true`，且不允许和单厂商预览同时使用；
- **同一个安全模型**：只走 stdio，不监听端口，不发起网络请求；项目目录在进程启动时固定，Quota-Flow 凭据不会通过 MCP 暴露；
- **同一个审计语义**：`nineflow_audit` 返回的 `verdict` 仍然是证据链、任务状态、上下文新鲜度的分层结论，而不是让 Agent 自己总结一句“看起来没问题”。

对一个开源项目来说，MCP 也是当下最自然的分发接口：用户不需要先学你的 CLI，只要在客户端里加九行 JSON，就能让 Agent 帮他查修订、取提示词、跑审计。约束只有被真正调用，才有价值。

## 九、工程落地时踩过的坑

这套东西不是一次写完的。几个真实的坑，值得单独说：

**1. Python 3.8 + 中文路径的测试发现问题**

在仓库根目录跑 `python -m unittest discover -s tests -t .` 会报 `Start directory is not importable`。最后改为进入 `tests` 目录执行 `python -m unittest discover -s . -t .`。这不是产品缺陷，但会浪费每个新贡献者的时间，所以写进了文档。

**2. 禁用模型后的陈旧变体**

早期构建不会清理 `context/shots`，禁用几个 provider 后，旧的每镜头文件仍然留在磁盘上。Context Pack 的统计是对的，但目录里躺着 160 多个“幽灵变体”。修复方式是在每次全量写入前清空 `context/shots`，并补了一个专门的回归测试。**共享目录的“删除”与“写入”必须一起设计。**

**3. 部分构建写共享包**

前面已经讲过。这个 bug 的教训是：只要一个命令既能“预览”又能“发布”，就一定会有人在错误的地方用它。把预览做成只读，比在文档里写十遍“不要这样用”更有效。

**4. Quota-Flow 0.1.0 的能力边界**

Quota-Flow 是这套编排层依赖的配额与模型调用基础设施。当前 CLI 版本是 0.1.0，能力边界必须如实标注：mock 与 handoff 可以先跑通，真实模型的下载、探测、失败路径要分别验证；不能把“计划支持”写成“已经支持”。这也是为什么演示项目默认先走 mock/handoff，而不是一上来就消耗真实配额。

**5. 本地看板的安全边界**

看板只监听本地，校验 Host/Origin，POST 需要自定义请求头，启用 CSP，不使用 `innerHTML`，文件访问被限制在 `refs/outputs/exports` 等允许根目录内，并支持 Range 请求。它不是公网服务，也不应该被暴露到公网。一个用来查看本地素材的工具，不值得冒远程代码执行的风险。

**6. JSON 错误输出到 stdout**

`refresh-hashes` 的失败信息最初被测试断言在 stderr，实际 CLI 约定是 JSON 走 stdout。测试失败提醒我们：**机器可读输出和人类可读输出必须有稳定契约。** 后来统一为 JSON 模式输出到 stdout，人类模式输出到终端。

## 十、结果：不是“完美一致”，而是“可解释的不一致”

目前这套系统在演示项目上的状态是：

- 62 个测试全部通过；
- 5 个镜头、4 个模型、20 个变体共享同一修订；
- 20 个变体累计引用参考图 56 次；
- 最近一次 mock 任务审计 13/13 通过；
- 真实 handoff 任务审计退出码 0；
- 下载视频经 ffprobe 校验为 5.0 秒、1920×1080、H.264；
- 九宫格输出 1920×1080，9 帧均匀采样；
- dashboard 可以查看分层审计结论、任务状态和九宫格；
- 7 个 MCP 工具可在 Claude Desktop / WorkBuddy 中直接调用，读写边界与 CLI 一致。

但我更想强调的是：**这套系统不保证“每个模型生成的画面完全一样”。** 它保证的是另一件事：

> 当画面不一致时，你能准确知道是哪一层不一致：是输入变了、状态错了、参考图没投影上、编译器漂了，还是模型自己没听话。

这两者的差别很大。前者是玄学，后者是工程。

## 十一、这套方法不解决什么

为了避免过度承诺，必须把边界写清楚：

- **不消除模型的随机性。** 同一个提示词、同一个种子，不同模型仍然会给出不同画面；同一模型的不同版本也可能不同。
- **不保证视觉质量。** 哈希锁管的是输入一致性，不是构图、光影、表演和剪辑节奏。
- **不替代导演与审片。** 九宫格和 ffprobe 只是把明显问题提前暴露，最终仍需人判断“这场戏对不对”。
- **不自动修复穿帮。** 它做的是发现、定位、阻断和留证，不是让模型自己变魔术。
- **依赖剧本的连续性纪律。** 如果时间线里的 `state_delta` 本身写错了，状态机会非常忠实地把错误传播到每一个模型。垃圾进，垃圾出，只是这次垃圾有哈希。

所以，NineFlow 的定位不是“AI 视频模型”，而是模型之上的**连续性编排与证据层**。它把“共享上下文”从一句口号，变成一组可计算、可拒绝、可审计的约束。

---

## 十二、结语：让随机发生在可控的边界内

回到开头那个问题：多模型协作时，角色为什么会穿帮？

因为每个模型都在独立地解释世界。你给它一段文字，它会补齐自己认为合理的细节；你给它一张图，它只会在自己的能力范围内参考。模型没有“上一镜”的概念，也没有“这个伤口是第 3 镜才出现的”这种时间感。

哈希锁解决的是“大家看的是不是同一份事实”；状态机解决的是“大家看的是不是同一时刻的事实”；确定性编译解决的是“大家拿到的是不是同一份指令”；分层审计解决的是“出问题时，能不能证明是哪一层先坏的”。

这四件事加起来，才让“跨模型一致性”从一个祈祷，变成一条可以工程化的路径。

> 一致性不是让模型不随机，而是让随机发生在可控的边界内，并且每一次都能解释。

代码与完整演示已经开源：

**https://github.com/bbo777/nineflow**

仓库里包含可运行的 mock/handoff 链路、5 镜头演示项目、62 个测试、13 项审计、7 个 MCP 工具、ffprobe 媒体校验和 ffmpeg 九宫格。你可以先不花一分钱配额，把整条链路跑通，再接入自己的模型。

如果这套思路对你有用，欢迎在 issue 里聊聊你遇到的穿帮现场。尤其是那些“明明用了同一张参考图，还是不像”的案例——它们往往不是模型的问题，而是上下文根本没有被锁住。
